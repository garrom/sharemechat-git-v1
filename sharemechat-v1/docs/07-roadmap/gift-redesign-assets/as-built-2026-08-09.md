## Cómo resuelve el icono (`GiftIcon`)

Por el `code` del regalo (de BD). **Orden actual (opción A, 2026-08-15): emoji primero, SVG después.**
1. **GRATIS → emoji unicode nativo.** Tanto las **caritas** (`CODE_TO_EMOJI`: `flirty 😉, hot 🥵, kiss 😘, laugh 😂, love 😍, ok 👌, sad 😢, wow 😮, basic 🙂`) como los **objetos** gratis (`OBJECT_CODE_TO_EMOJI`: `heart ❤️, star ⭐, fire 🔥, sparkle ✨, rosebud 🌹, labios 💋`). El emoji se pinta a **0.8× de su hueco** para igualar peso visual con los SVG.
2. **PAGO (premium) → SVG propio de marca.** `CODE_TO_SLUG`/`GIFT_ICON_SLUGS`: `rosa→rose, corona→crown, diamante→diamond`; y `cocktail, teddy, gift, ring, rocket` como slug directo.
3. **Fallback** (code no resoluble) → SVG genérico `#gi-gift`. **Ya NO se usa el `iconUrl` remoto** (los `.webp` daban 404 intermitente → imagen rota "no disponible").

**Decisión clave — opción A (2026-08-15):** los **objetos gratis se pintan SIEMPRE como emoji** (antes eran SVG), los mande el cliente o la modelo, para que el mismo objeto se vea **idéntico con independencia del emisor**. Motivo: en **random** la modelo solo puede enviar por chat/emoji (el canal de regalo-real es solo `CLIENT→MODEL` en backend, ver bitácora 2026-08-15), así que para no tener dos dibujos de la misma rosa se unificó todo a emoji. El **SVG de marca queda solo para los de pago**. Fuente única `OBJECT_CODE_TO_EMOJI` (exportada desde `GiftIcon`), compartida entre el render y el envío del modelo en random.

## Efectos (Fase 3) — desvíos

- Se derivan del **`tier`** (no de `animation_key`, que está NULL). No requiere backend.
- **Lo ven ambos lados** (emisor y receptor) porque se disparan al aparecer el mensaje en cada chat.
- **Solo mensajes recién añadidos**: se ignoran carga inicial de historial y recargas masivas (fix del bug "confeti en masa al seleccionar contacto"). Detección por diff de ids (`prevIdsRef`, `wasEmpty`, corte a >3 nuevos).
- Sin librerías (CSS keyframes inyectados + spawner DOM con `setProperty`). Respeta `prefers-reduced-motion`.
