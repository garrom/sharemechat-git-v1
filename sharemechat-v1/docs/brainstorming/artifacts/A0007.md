# A0007 — UX del pago cripto (NOWPayments): diagnóstico + mensaje a soporte

> Deliverable IA. Diagnóstico desde repo (ADR-051) + opciones reales de NOWPayments (web).
> El cambio de integración es CÓDIGO (tu sesión de dev); aquí va el análisis + el mensaje a enviar.

## Qué falló para el usuario (diagnóstico)

La integración actual usa la **Invoice API** de NOWPayments = **checkout alojado que REDIRIGE al
usuario FUERA de sharemechat.com** a `invoice.nowpayments.io` (ADR-051 §D2, línea 72 y 170). Eso
provoca la mala UX que viviste:

1. **Salida del dominio** → el usuario abandona sharemechat.com y aterriza en una página de otro
   dominio. Rompe la confianza y el contexto; parece menos profesional (ADR-051 §170 ya lo anticipaba
   como "fricción UX").
2. **Flujo multi-paso** → elegir moneda → ver QR → copiar dirección → pagar desde wallet externa →
   volver → esperar. Muchos pasos para un usuario no-cripto.
3. **Espera de confirmación** → la página `/checkout/success` hace polling cada 3s (máx 5 min); si el
   webhook tarda, muestra un spinner de "esperando confirmación blockchain". Sensación de incertidumbre.
4. **Errores de mínimos** → BTC en el pack de 10€ daba "amount less than minimal" dentro del selector y
   bloqueaba el botón (ADR-051 §200). Ya mitigado filtrando monedas por pack (P10 solo stablecoins).

## Cómo se mejora (opciones reales de NOWPayments)

- **★ Payment Widget embebido (SIN redirect)** — mantiene al usuario EN sharemechat.com, brand-matched
  (colores/fuentes/layout), campos personalizables. NOWPayments lo vende como mayor conversión. **Es el
  mayor salto de UX** y evita la salida de dominio. (Cambio de front: sustituir el `window.location.href
  = invoice_url` por el widget embebido.)
- **Branding de las páginas** — logo + colores + datos de empresa se aplican a invoices/widget desde el
  panel de NOWPayments (sección Branding, cambios en vivo). Barato, aplica ya aunque sigas con invoice.
- **Payments API (modal propio)** — control total de la UX en nuestro modal (se descartó en ADR-051 §D3
  por "más trabajo"). NOWPayments expone estados `waiting/confirming/confirmed/sending/partially_paid/
  finished/failed` → permite mostrar "confirmando en la cadena…" con progreso real en vez de un spinner
  congelado. Más dev, control máximo.

**Recomendación:** primero **activar Branding** (coste 0, panel) + evaluar el **Payment Widget embebido**
(mejor ratio esfuerzo/UX). El Payments API custom solo si el widget no basta.

>
> Hi,
> We run SharemeChat (custodial account, top-up "packs" credited to an internal wallet, currencies
> USDT TRC-20/ERC-20, USDC, BTC). Today we integrate via the **Invoice API**, which redirects users to
> `invoice.nowpayments.io`. We're seeing UX friction from the off-domain redirect and multi-step flow.
> Questions:
> 1. Can we use the **embedded Payment Widget (no redirect)** for our use case (dynamic amount per pack,
>    custodial, our order_id + IPN webhook), keeping users on our domain?
> 2. Does the widget support **brand-matching** (our logo/colors) and **restricting pay currencies per
>    order** (we hide BTC on small amounts due to minimums)?
> 3. Any option to **reduce steps** or show clearer **on-chain confirmation status** to the user
>    (waiting → confirming → finished) inside the embedded flow?
> 4. How do we enable **branding** on the current hosted invoice page in the meantime?
> Thanks — happy to share our merchant ID.
